优惠卷秒杀

添加优惠卷

实现voucher接口
@RestController
@RequestMapping(“/voucher”)
public class VoucherController {

@Resource
private IVoucherService voucherService;

/**
 * 新增秒杀券
 * @param voucher 优惠券信息，包含秒杀信息
 * @return 优惠券id
 */
@PostMapping("seckill")
public Result addSeckillVoucher(@RequestBody Voucher voucher) {
    voucherService.addSeckillVoucher(voucher);
    return Result.ok(voucher.getId());
}

}
这是添加优惠卷接口，之后通过apifox测试，成功添加100张秒杀优惠卷。

秒杀下单

实现voucher-order接口。下单时需要判断两点：
秒杀是否开始或结束，如果尚未开始或已经结束则无法下单
库存是否充足，不足则无法下单

下单流程：
A([开始]) –> B[提交优惠券id]
B –> C[查询优惠券信息]
C –> D{判断秒杀是否开始}
D – 否 –> X[返回异常结果]
D – 是 –> E{判断库存是否充足}
E – 否 –> X
E – 是 –> F[扣减库存]
F –> G[创建订单]
G –> H[返回订单id]
H –> Z([结束])
X –> Z

超卖问题

正常逻辑是线程一下单，查询库存，判断库存充足，扣减库存，然后线程二再循环。但是，在高并发场景下，可能会交叉执行，比如线程一在查询过程中尚未扣减库存时，线程二进入查询也没问题，会同时查询到库存充足，然后都扣减库存，导致库存不足。

解决方法

乐观锁和悲观锁，悲观锁是认为安全问题一定会发生，在操作数据前先获取锁，确保线程串行，但是性能不好。乐观锁是认为线程安全问题不一定会发生，不加锁，在更新数据时判断有没有其他线程对数据做更改，如果没有修改则认为安全，做数据更新，如果有修改则认为不安全，需要重试或异常。
这里使用乐观锁为解决办法，乐观锁常见的方式有两种，版本号和CAS。
版本号：在线程一查询时查询出库存和版本号，此时线程二插入进来查询库存和版本号，此时两个线程查询的结果一样，线程一扣减库存后，更新版本号，version字段的值会增加1，线程二查询时版本号对不上，不执行。
CAS：查询时只查库存，修改数据时判断实际库存数是否等于查询时的库存数，等于则执行，不等就不执行。
但是乐观锁会出现弊端，会出现有库存，但购买不到问题，所以将判断库存是否等于之前查询到的，改为是否大于0。
