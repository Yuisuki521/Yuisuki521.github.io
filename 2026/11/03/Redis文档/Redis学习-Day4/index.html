基于Redis实现Session登录

发送短信验证码

A([开始]) --> B[提交手机号]
B --> C{校验手机号格式}
C -- 不符合 --> Z([结束])
C -- 符合 --> D[生成验证码]
D --> E[保存验证码到 session]
E --> F[发送验证码]
F --> Z

短信验证码登录、注册

A([开始]) --> B[提交手机号和验证码]
B --> C{校验验证码是否一致}
C -- 不一致 --> Z([结束])
C -- 一致 --> D[根据手机号查询用户]
D --> E{用户是否存在}
E -- 存在 --> F[保存用户到 session]
F --> Z
E -- 不存在 --> G[创建新用户]
G --> H[保存用户到数据库]
H --> F

校验登录状态

然而集群环境下，session的共享问题是一个常见的问题，需要在多个节点之间同步session数据，以确保用户在不同节点之间的登录状态一致，多台tomcat并不共享session存储空间，当请求到达不同的tomcat服务时，会导致数据丢失问题，虽然说可以复制session数据，但是会增加存储成本，且在高并发环境下，复制session数据会导致性能问题。
所以，基于Redis实现session登录是一种常见的解决方案，它可以在多个节点之间同步session数据，以确保用户在不同节点之间的登录状态一致，同时也可以避免复制session数据导致的性能问题。
发送短信验证码时，生成验证码要保存到redis中，Redis中的value就用string类型，但是key不能直接用session的id，因为不同浏览器生成的session id是不同的，所以不能直接用session id作为key，而要使用手机号作为key。还有当我们短信验证码登录注册时，就可以根据手机号查询用户，校验验证码。登陆后保存用户到redis，这里我们保存的是一个对象所以用hash结构较好，也方便对单个信息增删改查，而且要将来方便客户端携带key，如果用手机号，会保存在前端浏览器不安全，所以我们用一个随机的token为key，最后我们还要把token给客户端，以后登录我们就可以基于token从Redis获取拿到用户信息。

拦截器校验登录状态

登录成功后，客户端每次请求都在请求头authorization字段携带 token，拦截器 preHandle方法的处理逻辑如下：
从request.getHeader(“authorization”) 取出 token，判空 — token 为空直接拦截，返回 HTTP 401 状态码
用LOGIN_USER_KEY + token 拼接 Redis key，通过opsForHash().entries() 取出 Redis Hash 中存储的用户数据 Map
判断 Map 是否为空 — 空则说明 Redis 中没有对应用户（token 过期或伪造），拦截返回 401
将 Redis 返回的 Map 转为 UserDTO 对象，存入ThreadLocal(UserHolder.saveUser)，方便后续业务代码直接获取当前用户
调用stringRedisTemplate.expire()刷新token的有效期，实现”活跃用户不过期”的效果

登录拦截器的优化

如果用户一直访问不需要登录的页面，拦截器就不会生效不会刷新token的有效期，导致用户登录过期。为了解决，我们可以在现在的拦截器前新加一个拦截器来做刷新工作，最后第一个拦截器做刷新，第二个做登录是否放行，调节拦截器优先顺序。
