Redis学习-Day9

2026/11/16 学习

一人一单

因为不能让同一个用户全部抢走所有商品，所以需要限制每个用户只能抢走一个商品
思路是这样的
A([开始]) –> B[提交优惠券id]
B –> C[查询优惠券信息]
C –> D{判断秒杀是否开始}
D – 否 –> X[返回异常结果]
D – 是 –> E{查询用户订单是否存在}
E – 存在 –> X
E – 不存在 –> F{判断库存是否充足}
F – 否 –> X
F – 是 –> G[扣减库存]
G –> H[创建订单]
H –> I[返回订单id]
I –> Z([结束])
X –> Z
但是经过测试发现出现问题，没有实现一人一单的效果，还是涉及到并发问题，但是这里是查询是否存在而不是修改数据，所以不用乐观锁，用悲观锁解决，从 查询订单 到 判断订单 到 新增订单 整体加锁，所以对这部分进行封装加锁加事务，加锁部分是针对同一个用户的操作，对用户id进行加锁。但是如果给这部分加锁，事务是等锁释放之后提交，在提交过程中可能其他线程会走进在数据库修改前进行操作，座椅这个锁加的范围有些小了，应该在return前加锁，是先获取锁再进入这个封装的方法。

一人一单的并发安全问题

模拟集群使用同一用户id进行操作，发现会出现一人可以下多单情况，两套jvm会有自己的常量池，锁监视器也不同，所以m个jvm至少都会有m个线程同时运行，要解决需要多个jvm使用同一个锁

分布式锁

分布式锁是要满足分布式系统或集群模式下多进程可见并且互斥的锁，分布式锁要满足 多进程可见 互斥 高可用 高性能 安全性等要求。
基于Redis实现分布式锁需要实现两个基本方法: 获取锁和释放锁。
获取锁需要利用setnx的互斥特性，确保只有一个线程获取锁，释放锁需要利用del命令删除锁，手动或超时释放。

获取锁和释放锁的流程

A([开始]) --> B[尝试获取锁]
B --> C{判断结果}
C -- nil --> D[获取锁失败]
C -- ok --> E[获取锁成功]
E --> F[执行业务]
F --> G[释放锁]
E -. 业务超时或服务宕机 .-> H[自动释放锁]
会出现问题

然而还会出现问题
问题一:比如线程一获取锁成功，，但是出现了业务阻塞，使其获取锁时间增长超过获取锁的超时时间，就会超时释放，这个时候其他线程就可获取锁成功，然后线程一业务执行完成，就会自动释放锁，然后线程二的锁被释放了，线程二还在做自己的任务，线程三也可以获取锁成功，此时线程安全会再次发生。
解决:这个时候要在释放锁的时候，判断锁标识是否是当前线程的就可以解决办法。
A([开始]) –> B[尝试获取锁](存入线程标识 UUID，因为多线程用线程id可能会重复)
B –> C{判断结果}
C – nil –> D[获取锁失败]
C – ok –> E[获取锁成功]
E –> F[执行业务]
F –> F1[判断锁标识是否是当前线程的]
F1 –> G[释放锁]
E -. 业务超时或服务宕机 .-> H[自动释放锁]
问题二:当线程一获取锁成功业务执行完成，然后判断标示是否一致，就会释放锁，但是这时释放时产生jvm垃圾回收阻塞，锁就不会释放，很可能会超过超时时间，其他线程来获取锁成功开始线程，线程一阻塞结束，释放锁，就把其他线程的锁释放了。
解决:这是需要把判断锁标识的动作和释放锁的动作需要变成原子操作，确保线程安全。使用lua脚本来解决多条命令的原子性问题。
问题三:基于setnx的分布式锁有以下问题:
不可重入:当a任务需要调用b任务，a拿锁，b也需要这把锁，但是b拿不到，所以成为死锁
不可重试:获取锁只尝试一次就返回false，没有重试机制
超时释放:仍存在安全问题。
主从一致性:比如主线程有了新数据，在给从线程传数据时，突然宕机，从线程就会丢失数据，其他线程可以拿到锁。
解决:使用Redission的分布式锁，它支持主从一致性，可以确保在主从集群下，锁的获取和释放是原子操作，不会因为主从一致性问题而导致锁的丢失。
